Put two people on the same task without telling them, and you usually get a mess. They both finish it, and now there are two answers that dont match and someone has to decide which one to throw away. No one decides this should happen. It comes from letting two people change the same thing without checking with each other first. That's why teams build so many small rules about who can do what. Standups. A lock on the deploy. One person who owns the release. The rules look like bureaucracy until the first time you skip one. Theyre what it costs to let more than one person change the same thing.

I built the maximal version of this with language models instead of people. And most days, if you asked me, I'd talk you out of needing it. Thats an odd thing to say when I build the thing, so let me make the case instead of just asserting it.

Smart people come down hard on both sides of this. I watched one well-regarded team argue in public that you [shouldn't build multi-agent systems](https://cognition.com/blog/dont-build-multi-agents) at all, the same week another put out a long, proud [writeup of one they'd built](https://www.anthropic.com/engineering/multi-agent-research-system) and shipped. So this isnt a question you settle by being smart. It depends on what you're building, and those two were building very different things.

People reach for several agents for a simple reason. One model feels limited, and adding a second feels like adding a person to a project, more hands and more done. That intuition is wrong, and it's worth being exact about why.

The expensive part of running several agents together isn't the models. Or it is, but not the way people expect. They budget for the model calls, so that's what they plan for. The real cost is getting the agents to agree with each other, and you can't design that away. It shows up the moment you have more than one of them, and it grows faster than their number does.

Two agents have one relationship to keep straight. Add a third and you don't add one relationship, you add three. A fourth takes you to six. What grows isn't the number of agents, it's the number of pairs that can disagree, because every new agent can interact with every agent already there. You add agents to get more done, but the pairs you have to keep in sync pile up even faster.

![A complete graph growing from two agents to eight. As each agent is added it has to connect to every agent already there, so the connections, the coordination cost, climb as n(n-1)/2 while the team grows by one.](./figures/coordination-explosion.svg)

*Add one agent. The team grows by one. The lines it has to keep in sync grow by the whole team.*

Reads and writes don't behave the same way, and that's where the trouble starts. Ten agents can read the same document at once, or a thousand, and it costs nothing but the reading. But if two of them write the same document, the writes have to be reconciled somehow, and that reconciling is the whole cost. You've seen this in any system you've run:

- One job waits on another that's waiting on it, and everything stops.
- A shared login hits its rate limit, and every task using it dies at once.
- A flaky step retries forever, burning money until someone notices and kills it.

In all of these the model did its job, and what failed was the system around it. The cost is in how much the agents share, not in how smart they are.

Distributed systems people named these failures decades ago. The write-write conflict. The lost update, where one change quietly buries another. The fixes are old, and they go two ways. You send all the writes through a single leader, so one wins and the other retries. Or you use something like a CRDT, which merges everyone's writes by a fixed rule. The second way is mostly closed to us. A CRDT can only merge mechanical state, and an agent's write is a paragraph of judgment from a writer that isn't even deterministic. No rule fuses two of those and keeps what each one meant. So we fall back on the oldest move there is. Keep two writers off the same thing, push them through one, and let the reads go to everyone.

![A diagram titled "writes do not parallelize": two agents write the same user profile as different shapes, a third agent merges them into a third shape, and the result cascades through incompatible structures, mismatched schemas, and broken endpoints into system failure. A green panel notes that reads do the opposite and combine cleanly.](./figures/write-conflict-cascade.svg)

*The same fact, drawn out. Two agents write one record as different shapes, a third tries to reconcile them, and the writes break the schema downstream. Reads combine cleanly. Writes don't.*

And the bill shows it. A multi-agent setup can burn [ten times the tokens a single chat would](https://www.anthropic.com/engineering/multi-agent-research-system), sometimes more, and that overhead is the coordination cost on your invoice. Every agent has to rebuild the context the others already have, say what it's doing, and hear what changed while it was working. The part the user asked for is a fraction of those tokens. The rest is the agents keeping each other current.

The long-run version of this is a kind of debt. Not the cost of building the system, the cost of keeping it coherent for as long as it runs. Every extra agent that can write to shared state is one more thing that can drift, and one more way to end up back at two people on one ticket. You pay it every day, every day the thing is running, and it gets worse the more writers you add.

You can't out-think this with a better model. A smarter model doesn't make the writes stop conflicting. The only two things that lower the cost are fewer agents or less sharing. Everything else only moves the negotiation around.

That last point runs backward from how people usually talk about it. The reason to split work across several agents is that one agent can't hold it all: too much context, too broad a task, a job too long for one loop to keep in its head. More agents were a workaround for a limit.

So when the model gets better, the case for several agents gets weaker. A better model holds more, reasons further, stays coherent longer. It removes the limit that made you split the work up in the first place. The better the model, the less you need to coordinate, because coordination was a tax on splitting, and you're splitting less. Every gain in capability is a reason to use fewer agents. But almost nobody reads it that way.

This is why I distrust most of what's sold as multi-agent. A plain program gets dressed up in the language of agents because that's the language with money behind it this year. That's not quite lying, it's branding. It's worth deflating, and the deflation is also a test you can run.

Take your system and rename every agent a function. Drop the names, the roles, the personas, and call them plan, research, and write. Now look at what's left. If plan calls research, gets a value back, and hands it to write, and you can read the whole thing as one program with some slow, unreliable subroutines, then you didn't have a multi-agent system, you had a plain program wearing a costume. One thing decided what happened next and called other things to do small, bounded jobs, and they answered and went away. That's an orchestrator and some tool calls. That's a fine thing to be, and it's what most systems should be, because we know how to make plain programs correct.

The interesting case is the one where the rename breaks. Now research and write are both running at once, both reaching into the same shared state. Neither is waiting on the other's return value, and each one's behavior depends on what the other did a second ago. That's a real multi-agent system, and it's the only place the coordination cost buys you anything. Everywhere else the costume was the only multi-agent thing about it. Which is good news, because a program is far easier to keep correct than a negotiation between things that don't fully agree.

And it isn't just me. When people have gone and [catalogued why these systems fail](https://arxiv.org/abs/2503.13657) in practice, it's the same two things every time, bad system design and agents talking past each other. The model reasoning badly barely comes up. A smarter model wouldn't fix what people most want it to.

I owe you the other side, because the system I built is overkill for almost everyone, me included most days, and I'd rather say that than sell it.

There is a band where the extra agents really are worth it. The easy version, behind most of the impressive demos, is work that's mostly reading. When the job is to explore many directions at once, and the material is bigger than one context can hold, you can point a dozen agents at it and let them read in parallel, because reads don't collide. Point a crowd of agents at a big research question and they'll beat a single agent badly, because nobody's stepping on anybody. Even people who spent a year skeptical of multi-agent setups tend to [come around on this exact case](https://simonwillison.net/2025/Jun/14/multi-agent-research-system/), and only this one: broad, parallel, bigger than one context. That case is real and it works, but it's the easy one. Nobody's writing in it, so there's nothing to keep in sync, and the hard part never comes up.

The version worth building for is the hard one, and it's hard for every reason above. Some work is too big and too structured for one mind to hold, and not because the context window is small. It has many parts that depend on each other, real division of labor, specialists you can't flatten into one prompt, and it runs longer than any one session. It's closer to running an organization than doing a task. Here the rename test breaks. Call them functions and the program stops making sense, because they aren't really subroutines. Each one carries context and judgment the others don't have, more than any single one of them could hold alone. You can't avoid the coordination here, so you build for it on purpose:

- roles with their own context and tools,
- clear ownership of who decides what,
- one layer whose only job is handing out work and reconciling the writes so the agents don't trample each other.

Even the people who first said "don't build these" have [landed in roughly the same place](https://cognition.com/blog/multi-agents-working). The setups that hold up keep writes single threaded and let the extra agents add intelligence, not more hands on the same state. The coordination cost is the same one I warned about. The difference is the work can't be done without paying it. So you pay it on purpose, and in return you get specialists who together hold far more than one mind can, kept coherent by a structure you designed instead of one that grew by accident. That's the hard part, and most of it hasn't been built yet.

The discipline is knowing which case you're in, because almost everyone who thinks they're in the hard one is in the easy one, or in neither. The structure is only worth building when the work can't be split any smaller. Wanting to build it doesn't count. If the whole thing fits in one prompt, keep it there. And if a single loop can run it, do that instead of splitting. Build the organization only when the work won't collapse into something simpler no matter what you try.

The one place it was clearly worth it for me was building the thing itself. OpenAcme is partly built and run by agents inside OpenAcme. One writes code, another handles releases, and a coordinating agent with its own memory tracks what's half-done and what's waiting on what. The work never sits still, because a bug a user files becomes code, which becomes a release, which becomes docs, which becomes the reply to the person who filed it. I ran it first as one careful loop, and it worked badly. I expected slow, thats the failure I'd braced for, but slow was never the issue. One mind holding all of it averaged everything together. Right after an angry bug report, the code it wrote came out timid and over-defensive. Then it would spend a morning deep in a refactor and start answering users like they were a stack trace, all terse, no read on the person. Splitting the work into separate agents, each with its own memory and its own narrow job, kept the engineering caution and the release discipline and the user's voice from collapsing into one gray average, which mattered to me more than throughput ever did. And a bigger model doesn't fix this part. Give one agent ten times the context and it still averages the roles it's holding. More room in one context isn't the same as actually separating the roles. I couldnt cleanly split the work apart either, because that one bug report ran through all of it, and the handoffs between roles were the part that mattered most. So each agent got its own identity, workspace, and memory, and the only thing they shared was the code and the tracker, which they reached through the coordinating agent, one write at a time. The moment the work stops being read only, a shared identity and a shared workspace are where two writers collide.

![Animated diagram of safe multi-agent collaboration: three agents, each with its own identity and workspace, send writes through one coordinator that serializes them one at a time into shared state, while reads flow back to every agent in parallel.](./figures/safe-collaboration.svg)

*How the write-heavy case works. Each agent keeps its own identity and workspace, writes as itself, and reaches shared state one write at a time through the coordinator, while reads go to everyone at once. Permissions keep the writes apart, not trust.*

So the engineering depends on which case you're in. For almost every system, the best thing you can do is make the agents act like one careful person. Send the writes through one path. Shrink what they share. Let one mind hold as much as it can, and split off only what it can't. For the rare system that really is the size of an organization, the work is the opposite, and harder. You build the structure that lets many specialists stay coherent without one mind holding it all. That second problem is the one I care about, and it's why I build OpenAcme, a self-hosted platform aimed at it.

And if your best design keeps sliding back to a single writer, you probably never needed more than one.
